# conex P0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Use superpowers:subagent-driven-development only when delegation has been authorized. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在空仓库交付可嵌入和独立运行的 broker 主干，通过同一个授权执行路径读取、列举和搜索 fs 与固定 HTTPS JSON catalog，并提供 TypeScript consumer。

**Architecture:** `.proto` 生成结构类型；方法注册同时绑定输入解码、资源授权提取和处理器。core 统一组织身份、策略、连接验证、凭据解析、限额和审计；fs 与 HTTP catalog 是独立 provider crate。HTTPS 入站及 inproc 都调用同一个 Host API，P0 不实现恢复会话或 blob 服务。

**Tech Stack:** Rust 1.94.0 / edition 2024、Tokio、prost 0.14 系列及兼容 pbjson、serde_json、Axum、Hyper 1、rustls/tokio-rustls、cap-std、cid/multihash、TypeScript/Bun、ts-proto、protoschema JSON Schema 插件。具体依赖在 Task 01 首次解析后锁定；后续只使用 lockfile，不依赖浮动 latest。

**Spec:** [设计 v6](../../design/2026-09-14-conex-design.md)，尤其 §0.1、§4–5、§8–9、§13、§14 P0 与 §16。完整后续路线见 [总路线图](2026-09-15-conex-roadmap.md)。本计划补充的 P0 方法参数与默认限制是实现决定；若执行时发现与更新后的设计冲突，先调整计划和向量。

## Global Constraints

来自设计的全局约束：

- “P0 不提供 Session 恢复、blob 服务或 sync；不提前实现未来全部端口。”
- “P0 必须支持 `raw + SHA-256`。”
- “不同 issuer 的同名 sub 不能合并。”
- “后者在对端身份、路由和调用权限确认后才能解析和发送”，其中“后者”指业务凭据。
- “P0 HTTP 的 Profile 由已配置 URL、协议版本及 Content-Type 固定”；binding 有效期默认 60 秒，每个 HTTP 请求独立认证。
- “未知方法或无法提取授权资源时 fail closed。”
- “后端必须声明支持等级；无法满足请求等级应拒绝，不能降级后返回成功。”P0 尚无内容存储后端，不声明这些等级。
- “新的传输请求不能生成新的 operationId 来绕开未知结果。”P0 只读，无持久 operation API。
- 设计中的默认值：timeoutMs=8000、maxInflight=4、maxFrameBytes=1048576、maxQueuedBytes=8388608；只有满足声明限制的方法/Profile 可广告。

P0 具体边界：Linux 首先验收；只读取 UTF-8 `.md`/`.org` 文本；单文档不超过 256 KiB，单目录/cursor 快照不超过 10000 项，单页默认 50/最大 100 项，搜索 query 为 1–256 字符的区分大小写字面子串，不实现正则、排序评分或写入。不能处理的内容返回明确错误，不返回假空文本。目录外的符号链接、非普通文件和非 UTF-8 路径不列入可访问资源。

P0 入站仅静态 bearer 和受信任宿主注入的 inproc 身份；OIDC 来源键有模型隔离测试，但不接受未实现验证的 JWT。真实 OIDC 登录、浏览器 cookie/ticket 在 P1。P0 HTTP catalog 的静态上游 API key 使用 env/file，必须在 TLS 对端验证后解析。

## 3. 契约实现决定

### 3.1 source 方法

ResourceId 是 UTF-8、斜杠分段的相对资源名：无空段、`.`、`..`、NUL、反斜杠或绝对路径；不进行 URL 解码或 Unicode 归一化。根目录用空字符串表示，但只允许在 list/search 的 root 字段中出现。授权按路径**段**比较，不用裸字符串前缀。

| 方法 | 请求 | 成功响应 | 资源与权限 |
|---|---|---|---|
| `source/list` | `root`, `limit`, optional `cursor` | `items: ResourceSummary[]`, optional `nextCursor` | 需要对 root 下整个子树的 list 许可 |
| `source/read` | `resourceId` | `resource: ResourceSummary`, `text`, `cid` | 需要精确资源或包含该资源的 read 许可 |
| `source/search` | `root`, `query`, `limit`, optional `cursor` | `items: SearchHit[]`, optional `nextCursor` | 需要对 root 下整个子树的 search 许可；不能读全源再过滤越权结果 |

ResourceSummary 字段为 `resourceId, title, mime, optional sizeBytes, optional revision`；SearchHit 为 `resource: ResourceSummary, excerpt`，excerpt 最多 512 字符。revision 是内容快照的 opaque 标识：read 使用返回内容的 CID；list 可以省略 revision，不以 mtime 当条件写版本。

list/search 的分页由 provider 的有界快照缓存支持：最多每主体/provider 4 个快照，租约 60 秒，包含规范化 root/query、主体/租户、策略版本、当前位置；cursor 使用随机句柄，不让客户端自行拼偏移和来源。每页仍授权，过期/不匹配返回 bad_request；不承诺原数据后续变化实时反映在该快照。快照项数或总字节超过预算时 quota_exceeded，不能截断后假称完整。

### 3.2 JSON-RPC/HTTP

固定入口 `POST /rpc`，请求 Content-Type 为 `application/json`，Profile 为 `conex-jsonrpc2-http-v1`。P0 WSS 未实现，不能列在 hello 的支持列表。JSON-RPC 业务请求形态：

```json
{
  "jsonrpc": "2.0",
  "id": "01ARZ3NDEKTSV4RRFFQ69G5FAV",
  "method": "source/read",
  "params": {
    "context": {
      "providerEndpointId": "notes-local",
      "plane": "broker",
      "bindingId": "opaque-server-issued-binding"
    },
    "timeoutBudgetMs": 8000,
    "input": { "resourceId": "team/design.md" }
  }
}
```

`conex/hello` 在没有 binding 的已认证请求中调用，输入 `profileId, plane, provides, requires`，成功返回 bindingId、60 秒期限、固定 Profile 和能力/限额。binding 绑定主体、租户、入口 audience、协商结果；不是身份凭证。业务请求也支持同路径的 inproc API，inproc 不要求 HTTP binding。

hello 同样使用 CallParams 包装：`context.plane=broker`、`context.providerEndpointId` 为空且不带 binding，`input` 是 HelloRequest；input.plane 必须与 context.plane 相同。只有控制方法允许空 endpoint，业务方法必须填写已安装 endpoint。HelloResponse 的期限字段固定为 `expiresInMs:uint32=60000`；包含 `profileId,plane,provides,rejectedCapabilities,limits`，限额字段由 common.proto 定义并生成。SDK 测试与 HTTP 服务共用这一约定。

认证失败为 HTTP 401；错误媒体类型为 415；超过 body 限制为 413；其余已解码 JSON-RPC 调用成功或业务错误均返回 200；有效通知执行后返回 204 且无 JSON-RPC 响应。不接受 batch；入站 server 收到孤立 response 对象时拒绝并审计。无 ID 的错误请求无法关联时用 JSON-RPC id:null，不把格式错误当有效通知忽略。

错误数值由 common.proto 的 ErrorCode 枚举**一次冻结全表**（设计 §5.2）：parse_error=-32700、bad_request=-32602、unknown_method=-32601、internal=-32603；unauthorized=-32001、forbidden=-32002、unknown_provider=-32003、unsupported_capability=-32004、unavailable=-32005、timeout=-32006、payload_too_large=-32007、quota_exceeded=-32008、plane_mismatch=-32009、peer_untrusted=-32010、cancelled=-32011、outcome_unknown=-32012、stale_revision=-32013、conflict=-32014、slow_consumer=-32015、bad_blob=-32016、session_lost=-32017、resume_unavailable=-32018。`-32019..-32099` 预留且不得改号或复用。枚举零值 `unspecified` 不可作为业务结果。`error.data.code` 从枚举描述符生成小写语义名，不能另手写一套映射表；未实现阶段的方法不广告，但其码已在表内。

### 3.3 方法注册与授权执行

core 按 `(providerEndpointId, protocol, version, method)` 获取已安装的 Route。工厂注册按 `(kind, protocol, version)`；`kind=source-fs` 与 `source-http-catalog` 是两项数据，host 只在装配根注册工厂，不在 dispatch 中分支。

每个 Route 固定可选出站 TargetId 和 CredentialKey。执行顺序：输入解码/资源提取 → 认证主体映射 → 策略 → 预留审计与执行限额 → 连接并验证目标（若存在）→ 复核策略 → 解析凭据（若存在）→ handler → 输出 schema 校验 → 完成审计。Request.context 的字段仅用于选择目标，不接受客户端伪造 principal/policyVersion。

## Task 02：冻结 P0 消息、方法、清单和错误契约

**Files — Create:** `schema/conex/v1/{common,rpc,control,manifest,source}.proto`；`crates/conex-proto/src/{wire,validation}.rs`；`crates/conex-proto/tests/wire.rs`；`sdk/typescript/tests/wire.test.ts`；`conformance/vectors/p0/wire.json`；`docs/contracts/p0-wire.md`。**Modify:** proto lib/build 导出、Task 01 生成产物。

**Interfaces:** `decode_wire(&[u8]) -> Result<v1::Message, ProtocolError>`、`encode_wire(&v1::Message) -> Result<Vec<u8>, ProtocolError>`、`validate_message(&v1::Message) -> Result<(), ProtocolError>`；ProtocolError 为 `{rpc_code: i32, request_id: Option<String>, message: String}`。v1 的业务参数与结果通过 google.protobuf.Value 表达，具体 input 由方法注册引用生成消息类型。

- [x] 按 §3.1/3.2 的字段定义 source/control/manifest 类型；common 定义 Limits、Plane、ErrorCode、Error；每个字段记录 tag、presence、长度上限，不复用已分配 tag。P0 只允许 broker，relay 枚举可识别但拒绝使用。消息骨架如下：

```proto
message Message {
  oneof body {
    Request request = 1;
    Success success = 2;
    Failure failure = 3;
    Notification notification = 4;
  }
}
message Request {
  string request_id = 1;
  string method = 2;
  CallParams params = 3;
}
message CallParams {
  RequestContext context = 1;
  uint32 timeout_budget_ms = 2;
  google.protobuf.Value input = 3;
  // 4/5 为 operationId/meta 预留，P0 不使用也不得改号或复用（设计 §5.2）
  reserved 4, 5;
  reserved "operation_id", "meta";
}
message RequestContext {
  string provider_endpoint_id = 1;
  Plane plane = 2;
  optional string binding_id = 3;
}
```

Success 为 `request_id:string(1), result:Value(2), reserved 3`（meta 预留）；Failure 为 `optional request_id:string(1), error:Error(2), reserved 3`（meta 预留）；Notification 为 `method:string(1), params:CallParams(2), reserved 3`（meta 预留）。Error 为 `code:ErrorCode(1), message:string(2), diagnostic_id:string(3), execution:string(4), retry:string(5), optional details:Value(6)`，execution/retry 仅接受设计列举值。Plane 枚举为 unspecified=0、broker=1、relay=2；实际请求必须明确指定 broker。control 的 hello 输入/输出与 Manifest 按设计对应字段建模，不引入源码路径/进程命令字段。

- [x] 建立具体失败用例：ULID 字符串往返；通知无 id；成功没有 method；错误 code 和 requestId 保留；success/error 同时出现、重复 JSON key、batch、非法 ULID、遗漏 plane、超深嵌套拒绝。Rust 示例：

- [Hyper连接级API](https://hyper.rs/guides/1/client/basic/)与[tokio-rustls](https://github.com/rustls/tokio-rustls)用于分离连接验证与业务请求；没有验证前先解析/附带上游秘密的快捷路径。
- [cap-std Dir](https://docs.rs/cap-std/latest/cap_std/fs/struct.Dir.html)提供相对目录能力操作；真实symlink/竞态测试仍是发布前提。
