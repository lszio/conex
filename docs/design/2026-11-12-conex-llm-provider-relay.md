# Conex LLM 提供者与中继：架构增补

> 日期：2026-11-12。状态：方向与三个关键决策（OpenAI 兼容入口 / LLM 中继先行 / 总览+详情工作台）已由用户确认；地基于 2026-11-13 交付（领域契约、节点适配、hub 网关、模型服务视图，`cargo xtask e2e --suite private-llm` 全过，部署见 [运行手册 §4](../runbooks/private-mvp.md)）。L05–L07（omniroute 实接与两机公网 live）与增量流式扩展未完成，验收以实际证据为准。
> 权威范围：LLM 提供者领域、中继暴露、hub OpenAI 兼容入口与工作台总览形态。其余定位、对象与安全边界仍以 [MVP 架构基线](2026-10-29-conex-private-platform.md) 为准；本文是领域增补，不替代基线。

## 1. 定位与动机

用户核心诉求：一个核心工作台，把不同地方的设备、服务、Agent、模型接进来，在同一平台观察与操作。典型场景是家庭模型服务经 conex 公共服务暴露给外部工具——像代理与中继。上游不绑定具体产品：节点侧适配器对接 **OpenAI 兼容上游**，首实例为用户已部署的 omniroute（自托管聚合网关，一个 OpenAI 兼容端点后路由多个 LLM 提供者）；Ollama 的 `/v1` 面、vllm、LM Studio 等同属该兼容面，接入不新增适配器。

这不是改架构：hub + 自治节点 + 领域适配器、直连/转发双路径正是基线形态，P2/P5/P7 已交付底座。本增补做两件事：

1. 把「LLM 提供者」从 Agent 后端背后提升为一等领域——现在模型只能经 OMP/Codex 会话间接使用，没有可中继、可管理、可被外部程序消费的模型服务概念。
2. 给 hub 增加一个**受约束的协议翻译入口**（OpenAI 兼容），让任意外部工具以 `base_url + API key` 的方式消费已获准的模型能力。

不是：通用隧道、任意 URL/端口代理、多用户 API 市场、计费系统。网关只翻译**已发布且获准的 Conex 能力**，是基线 §10.1「公网入口仅转发已发布且获准的能力」的一个具体翻译边缘，不引入新的转发自由度。

## 2. 领域对象

| 对象 | 身份与责任 |
|---|---|
| LlmProvider | 节点上的模型服务入口，关联适配器实现、上游地址与健康状态；一个节点可有多个 provider |
| LlmModel | provider 发布的模型：名称、家族、上下文窗口、支持能力（tools 等）；未知能力标注 unknown，不伪造 |
| LlmApiKey | hub 对外凭据；SHA-256 摘要入库，带范围（允许的模型/提供者）、有效期与撤销 |
| LlmRoute | hub 侧映射：key → 允许的模型 → 已批准发布该模型的 relay-allowed provider |

- **无会话对象**。LLM 调用是一次能力调用；对话历史由调用方（外部工具或平台内消费者）自带。conex 不存储 prompt/正文，与基线 §11「中心默认不持久化完整对话正文」一致；usage/token 计数不是正文，可持久化。
- 同一模型名被多个 provider 发布时存在路由歧义：key 必须显式绑定 provider，否则网关拒绝该模型并明确报错，不静默选择。

## 3. 领域契约（首版）

- `llm/providers/list`：本节点 provider、模型、健康与最近延迟；一次查询，不单设 models 操作。
- `llm/chat`：一次补全。输入 messages/model/params（含 stream 意图）；输出为增量事件（delta）+ 终态（finish 原因、usage、代际）。取消语义沿用调用路由：固定代际取消、发送边界后失联为结果未知、不自动重放。
- tools/function-calling 仅当上游适配器真实支持并探测通过才声明；不支持即明确报错并让调用方降级。
- 最终操作名随生成链落定为 `llm/providers/list` / `llm/chat`；独立契约页随 omniroute 实接回写（`docs/contracts/llm-provider.md`）。

## 4. 节点侧

- llm 模块是节点普通领域模块（与 metrics/relations 同级），经正常发布导出自身契约；不是中心功能，也不内嵌进 Agent 适配器。
- 适配器对接 **OpenAI 兼容上游**（`/v1` 面，首实例 omniroute）；上游地址与凭据留在节点配置，不出节点。适配器把上游差异映射为领域契约，缺失元数据标 unknown。
- 上游内部的路由、负载均衡与回退对 conex 透明：conex 只看到上游暴露的模型面，不感知也不承诺上游背后的具体后端。上游模型列表可能很大且动态，provider 发布支持配置筛选（allowlist），不盲转全量列表。
- provider 健康与模型列表有缓存与失效；上游不可达如实报告，不用过期数据冒充在线。
- 导出策略沿用基线：`relay-allowed` 才可被 hub 网关路由；`direct-only` 只能平台内（获准直连）消费，且不得经组合模块绕道泄漏（派生导出须明确获准数据范围）。

## 5. hub OpenAI 兼容入口

| 关注点 | 决定 |
|---|---|
| API 面 | 首版 `/v1/models` 与 `/v1/chat/completions`；`stream:true` → SSE **整段单帧 + 终帧 + [DONE]**（中继路径上结果已完整到达，不伪装打字机；增量分帧属后续契约扩展），`stream:false` → 单响应。embeddings 等其余端点不做，不冒充完整 OpenAI API |
| 鉴权 | Bearer LlmApiKey；范围、有效期、撤销；网关在 hub 内，撤权即时生效（无节点直连的离线窗口） |
| 路由 | model → 已批准且 relay-allowed 的 provider → 经既有转发路径调用节点；路径改变不扩大授权 |
| 正文边界 | prompt/completion 仅在转发期间内存中处理；不落盘、不进日志、不进错误转储（canary 纳入验收）；usage 计数可入库 |
| 有界性 | 每 key 并发上限、请求体上限、生成时长预算；沿用调用路由的截止时间与取消机制 |
| 断开语义 | 客户端断开触发调用取消并尽力通知上游停止生成；「取消已请求不等于后端已停止」条款继续适用，如实上报 |
| 失败区分 | key 无效/过期/撤销 → 401；越权模型 → 403；模型不存在 → 404；节点离线 → 明确 5xx；生成中断 → 结果未知。不静默返回空成功 |

E2EE 首版不承诺：网关是受信组件，能接触转发明文（基线 §10.3 已有条款，此处重申适用于 LLM 正文）。

转发路径的两项实施事实（e2e 实证，2026-11-13）：

1. **转发预算受发布链路协商 timeout_ms 约束**（默认 8s，两端取小）。LLM 调用普遍超过 8s，为此新增批准配置：hub 顶层 `wss_link_timeout_ms` 与节点 `[publication] link_timeout_ms`（均 1000..=600000）。逐调用预算仍由调用方携带并受该上限约束——抬高上限不自动拉长单个调用。
2. 中继回复经 pbjson Value 往返，整数退化为 f64；网关投影前按 `normalize_numbers` 归一（与 HTTP /rpc 路径同一惯例）。

注册记账主体是发布链路的认证 principal（`registry.register` 以链路 principal 为 node_id 记账）：`[[capabilities.publish]].node_id` 填节点 `[[tokens]].principal_id`，不是节点 ULID。

## 6. 工作台：总览 + 详情

用户已确认工作台形态调整为「总览 + 详情」：

- 新增**总览页**：一屏集中展示节点、已发布服务/能力、Agent、模型服务、服务器健康；点击进入现有领域视图（会话/图谱/服务器/模型）。数据来源是 hub 目录投影与各视图既有查询，不新增第二事实源。
- 新增**模型服务详情视图**：provider/模型/健康/延迟/最近调用用量（计数，非正文）。
- API key 的签发与撤销首版经配置/CLI 完成；Web 管理界面是后续项，本包不承诺，不预建占位界面。

## 7. 验收矩阵 L01–L07

| ID | 必须观察到的结果 |
|---|---|
| L01 | 外部工具（真实 OpenAI 兼容客户端）经 hub 流式调用模型：增量、终态与 usage 正确；stream:false 同样正确 |
| L02 | key 负路径：无效/过期/撤销 → 401，越权模型 → 403，模型不存在 → 404；凭据与正文不出现在 hub 日志/磁盘（canary） |
| L03 | 节点离线 → 明确 5xx；生成中断 → 结果未知语义明确，不自动重试 |
| L04 | direct-only 或未批准的 provider 不可经网关调用；relay-allowed + 已批准才可达 |
| L05 | 客户端断开触发取消：上游生成停止，或未停止被如实标注 |
| L06 | 工作台总览与模型服务视图展示真实健康与用量；断连转 stale，不用演示数据填空 |
| L07 | 两机真实链路：家庭节点（OpenAI 兼容上游，首实例 omniroute）↔ 公网 hub ↔ 外部网络中的工具，L01 在真实公网拓扑下通过（吸收原 P9 两机场景；A02 证据可共享） |

## 8. 调查与未验证边界

- omniroute 实例的实际行为以探针为准：模型列表规模与命名、SSE 增量形态、tools 透传与否、usage 字段、鉴权头；不按其在线文档盲接。「OpenAI 兼容」各实现有差异（omniroute、Ollama `/v1`、vllm……），适配器按公共面实现，实例差异在接入时探针确认，不做无限兼容承诺。
- hub 现有转发路径承载流式 delta 的行为需探针确认，不假设与直连一致（截止时间、预算、事件流在 relay 下的表现）。
- hub HTTP 层与前置反代（Dokploy、家中反代）对 SSE 的缓冲行为需实测；反代缓冲会破坏流式，部署时必须验证。
- usage 计数的口径（上游报告 vs 自算）取决于适配器探测结果；取不到就标 unknown，不估算冒充。
