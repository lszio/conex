## 1. 范围

P1 在 P0 主干上扩展：

- 两条 WSS Profile（`conex-jsonrpc2-wss-v1`、`conex-protobuf-wss-v1`）通过 `conex-transport-ws` 状态机握手。
- `conex-agent` 反连入口：`agent/register|heartbeat|resolve` 三方法 + in-memory 注册表。
- 持久化存储：`conex-content`（`cap-std` 受限根 + `tmp+rename` 写 + `recover()` 崩溃恢复 + 引用计数 GC）。
- 副作用治理：`conex-core::operation`（dedup key + 24h TTL + crash recovery + GC）。
- 会话/附件：`conex-core::session`（绑定 + epoch fencing + 120s 租约 + GC）。
- 浏览器入口：`conex-host::agent::HostSide`（OIDC code+PKCE + 30s ticket + 主体/访问绑定）。
- `conex-host::broker` 单一业务入口：HTTP `/rpc` 与 WSS `/wss` 共用 dispatcher，契约严格解码 + 输出校验。
- 公共类型：`conex-proto::cid` 唯一内容寻址函数（`contentCid` + `manifest_tree` + `addressing_for_parts`）覆盖 P0/P1。
- 设计 §14 P1 七项均已被 P1-02/03/06/07/08/05/09 切片覆盖；P1-10 联合验收由 `crates/conex-host/tests/p1_e2e.rs` 在 in-memory 内完成端到端 broker 调用循环。

## 2. 启动最小主机

最小 `host.toml` 同时启用 source/fs endpoint 与 P1 持久化后端（content/session/operation）：

```toml

audience = "broker.local"

[tls]
cert = "/etc/conex/host.pem"
key  = "/etc/conex/host.key"

[[tokens]]
token_hash = "<sha256 of bearer token, hex>"
principal_id = "alice"
tenant_id = "tenant-a"
audience = "broker.local"

[[policy]]
principal_id = "alice"
tenant_id = "tenant-a"
endpoint_id = "notes-local"
actions = ["list", "read", "search"]
root = ""
subtree = true

[[endpoints]]
id = "notes-local"
tenant_id = "tenant-a"
provider_id = "source"
kind = "source-fs"
provides = ["source/list", "source/read", "source/search"]
root = "/srv/notes"

# P1 持久化后端（开发环境；生产环境把 root 改为受控路径并加文件锁）

```

启动：

```bash

source .toolchain/env.sh
cargo run -p conex-host -- host.toml
```

## 3. 鉴权与会话入口

| 入口 | HTTP | WSS |
|---|---|---|
| 静态 Bearer（注册令牌） | `Authorization: Bearer <token>` | 不直接使用；通过 OIDC → ticket → WSS handshake |
| OIDC code+PKCE | `POST /oidc/authorize?principalId=&tenantId=&origin=&audience=&code_challenge=&code_challenge_method=S256` | — |
| OIDC code 兑换 | `POST /oidc/token` JSON `{ code, code_verifier, origin }` | — |
| 一次性 ticket | `POST /tickets` JSON `{ principalId, tenantId, origin, targetHost, peerRole, capabilityCaps?, sessionId? }` | — |
| 会话握手 | — | `/wss`：`conex/hello` → 服务端发 `negotiationId` → `conex/ready`（10s 超时） |
| 业务帧 | `/rpc` JSON-RPC envelope | `/wss` 同 envelope，ready 之后才可投递 |

绑定（session）：

| 方法 | 用途 | 关键约束 |
|---|---|---|
| `session/open` | 创建 Session + 首个 attachment，绑定 principal+tenant+provider+plane | `recovery ∈ {none, in_process, persistent}`（persistent 在 P1 demo 降级为 in_process） |
| `session/resume` | 用 `expectedEpoch` fencing 旧 attachment | epoch 不匹配返回 `resume_unavailable` |
| `session/renew` | 仅延长当前 attachment 租约 | epoch 必须等于当前值 |
| `session/close` | 终态 | 终态 attachment 不可复活；最后一个 attachment 关闭 → 删除 Session |

## 4. 业务方法（broker dispatcher 单一入口）

| 命名空间 | 方法 | 持久化后端 | 备注 |
|---|---|---|---|
| `blob/*` | `put, chunk, commit, pin, unpin, have, get, cancel` | `conex-content` | `commit` 由服务端按上传自身 receipt 重算根（不接受客户端叶子列表）；坏块 → `bad_blob` |
| `session/*` | `open, resume, renew, close` | `conex-core::session` | 128 KiB Staging TTL 由 `attachment_lease_ms` 控制 |
| `operation/*` | `get, cancel` | `conex-core::operation` | dedup key = (tenant, principal, provider, space?, resource, method, operationId)；TTL 24h |
| `agent/*` | `register, heartbeat, resolve` | `conex-host::agent` | `hostOrigin` 必须以 `conex://` 开头（反欺骗） |

## 5. 内容寻址与多块资源

`conex-proto::cid` 是规范实现，唯一函数 `content_cid(bytes, chunk_size)` + `manifest_tree(...)` + `addressing_for_parts(...)`。

- `len <= chunk_size` → CIDv1 raw/SHA-256。
- `len > chunk_size` → `ChunkManifest`（protobuf wire，1024 entries/层，>1 层自动分层）。
- 黄金向量由 `conformance/tools/gen_manifest_goldens.py` 用 `protoc --encode`（C++ protobuf）+ Python 标准库独立生成，与 prost / ts-proto 逐字节一致。
- 修改规范字节要 bump `formatVersion`，重算黄金。

`source/read` 与 `blob/*` 使用同一函数；fs/http-catalog 的 `MAX_DOC_BYTES = 256 KiB`，所以读取路径不会跨 chunk_size，但行为不变。

## 6. 错误码 → 业务策略

`conex_proto::v1::ErrorCode` 在 wire 与 Rust 之间统一：

| Code | 触发 | 业务处理 |
|---|---|---|
| `BadBlob` | commit 重算根失败 / 长度不符 / 块被篡改 | 不要盲重试；重传整段 |
| `ResumeUnavailable` | epoch 不匹配 | 重新 `session/open` |
| `SessionLost` | attachment 租约过期 | 重新 `session/open` |
| `Conflict` | 同 operationId + 不同 param_digest | 修正参数后重新发起 |
| `OutcomeUnknown` | operation 已发送但未确认 | **不自动重试**（design §7.3） |
| `Unauthorized` | binding / ticket / OIDC 校验失败 | 重新建立身份 |

## 8. 已记录的缺陷（不阻塞）

- 跨进程 Session 恢复（host 重启）：不在 P1 范围，返回 `session_lost`。
- 反连 agent 的实际双向 WS：依赖外部隧道，CLI 形态可离线调用；host 接受 in-memory 注册。
- OIDC 的 issuer / audience 真实签名验证：当前只校验 origin + PKCE 哈希。
- 1 GiB 真实弱网续传：依赖 P1-04 Stream 帧内嵌块字节；当前 in-process store 可承载，wire 端仍未暴露 `blob/get` 链路（属 P1-08 wire 闭环）。
